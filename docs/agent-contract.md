# Agent contract

What an agent records in inkentry memory, when, and how it links each entry.
The agent skill carries a copy of this document and the Claude Code hooks
prompt from it, so what is written here is what an agent is asked to do.

Needs inkentry 1.2.0 or later for `--reconcile` and its resolution flags,
`memory tags`, `--file` and `memory anchor`. On an older CLI, write with a plain
`memory add` and search before you write.

## 1. The bet

The calling agent is the extractor. It was in the conversation, it has read
the code, and it is a stronger model than anything inkentry would run on the
result. So inkentry stores, indexes and retrieves what the agent writes, and
never judges it: no model reads an entry to decide whether it is worth keeping,
and nothing rewrites it afterwards. The consequence is that the quality of
memory is the quality of what the agent writes. This document is what it is
asked to do.

## 2. Kinds

Pick the kind by what the entry is, not by how important it feels.

| Kind | It is |
|---|---|
| `decision` | A choice between alternatives, made. |
| `requirement` | A constraint stated by the human or imposed by the environment. The agent did not choose it. |
| `antipattern` | Something tried and rejected, with why. |
| `note` | An observation worth keeping that is none of the above. |
| `context` | Standing background that explains why the project is the way it is. |
| `intent` | Work in progress that others should not collide with. |
| `question` | Something open that someone has to answer. |
| `answer` | The resolution of a recorded question. |
| `handoff` | Where the work stands when a session ends. |

A quick test when two kinds fit: if you picked between options, it is a
`decision`; if someone told you, it is a `requirement`; if you tried it and took
it out, it is an `antipattern`.

### decision

**Belongs.**

- Title: `Chose bcrypt over argon2 for password hashing`
- Body: Passwords are hashed with bcrypt at cost 12 in `src/auth/hash.rs`.
  Argon2 was rejected because the production image has no libargon2 and adding
  it would break the static musl build. Revisit if the image changes. Affects
  login and password reset.

**Does not belong.**

- Title: `Fixed the login bug`
- Body: Changed the token check in `src/auth/session.rs` so it no longer rejects
  tokens that expire in the same second.

A fix is not a choice between alternatives. It belongs in the commit message.

### requirement

**Belongs.**

- Title: `Login p95 latency limit of 200 ms`
- Body: The maintainer stated that login p95 latency must stay under 200 ms,
  measured on the CI reference runner. Any change under `src/auth/` has to be
  benchmarked against it.

**Does not belong.**

- Title: `Use a connection pool for the database`
- Body: The agent proposed a pool and the human agreed.

The agent made that choice, so it is a `decision`, with the alternatives it
rejected.

### context

**Belongs.**

- Title: `Billing runs as a nightly batch, not per request`
- Body: Invoices are generated by the job in `jobs/invoice.rs` at 02:00 UTC from
  the previous day's usage rows. Nothing in the request path writes an invoice,
  so latency work on the API does not affect billing.

**Does not belong.**

- Title: `Sprint goal is finishing the importer`
- Body: This sprint is about the CSV importer.

That is a status, and it is stale in two weeks. It belongs in an `intent` or a
`handoff`, or nowhere.

### note

**Belongs.**

- Title: `Test suite fails on macOS when TMPDIR resolves through a symlink`
- Body: `tests/fs_walk.rs` compares canonical and non-canonical paths and fails
  when `TMPDIR` goes through `/var` to `/private/var`. Running with
  `TMPDIR=$(cd "$TMPDIR" && pwd -P)` passes. The test is not fixed.

**Does not belong.**

- Title: `Read src/auth/hash.rs and src/auth/session.rs`
- Body: Looked at how hashing is wired into sessions.

That narrates what the agent did. It says nothing the next reader can use, and
the files are still there to read.

### intent

**Belongs.**

- Title: `Refactoring the token bucket to per-key limits`
- Body: Working in `src/ratelimit/`. Expect changes to `bucket.rs` and
  `middleware.rs` until branch `feat/per-key-limits` merges. Written with
  `--files src/ratelimit/bucket.rs,src/ratelimit/middleware.rs` so an overlapping
  session is warned. Archive it with `inkentry memory archive <id>` when the work
  is done.

**Does not belong.**

- Title: `Should probably rework the limiter at some point`
- Body: The limiter is getting messy.

That is a wish. Put it in an issue, or record it as a `question` if someone has
to answer it.

### answer

**Belongs.**

- Title: `verify re-embeds from stored chunk content`
- Body: Answers "should verify re-embed from disk or from stored chunk content?".
  From stored chunk content: it avoids file I/O and matches what was indexed,
  while the file on disk may have changed since the last index. Written with
  `--relates-to <id of the question>`, which is what closes the question.

**Does not belong.**

- Title: `Use Postgres advisory locks for the job queue`
- Body: Advisory locks avoid a second lock service.

Nothing was asked, so nothing is answered. A choice with no recorded question
is a `decision`.

### handoff

**Belongs.**

- Title: `Handoff: per-key rate limits, middleware not wired`
- Body: Done: token bucket in `src/ratelimit/bucket.rs`, with tests. Next: wire it
  into `src/http/middleware.rs`, add the `rate_limit.per_key` config key, update
  `docs/config-reference.md`. Open: whether counters should survive a deploy.
  Branch `feat/per-key-limits`, last commit `a1b2c3d`.

**Does not belong.**

- Title: `Handoff: session summary`
- Body: Read the code, ran the tests, edited three files, ran the tests again.

That is a log. A handoff says what is done, what comes next and what is open.
Anything decided along the way is its own `decision`, not a line in the
handoff.

### question

**Belongs.**

- Title: `Should rate-limit counters survive a deploy?`
- Body: The token bucket in `src/ratelimit/bucket.rs` keeps counters in memory,
  so every deploy resets each key to full. Unknown whether that is acceptable for
  the paid tier. Options: persist counters in Redis, or accept the reset. Needs
  an answer from the maintainer.

**Does not belong.**

- Title: `How do I run the tests?`
- Body: Not sure which command runs the suite.

The repository answers that. Search or read it instead of recording it.

### antipattern

**Belongs.**

- Title: `In-process cache for search results`
- Body: Tried an LRU cache in front of `search()` in `src/search/mod.rs`. Hit rate
  stayed under 3% because queries rarely repeat, and results went stale after an
  index refresh, which failed two tests. Removed. Do not retry without a query
  log that shows repeats.

**Does not belong.**

- Title: `Forgot --features when running cargo test`
- Body: The first run failed because the feature flag was missing.

A slip is not a rejected approach. Nobody will be tempted to repeat it.
Never use an `antipattern` for a rule the human states ("never use
`unwrap()`"); that is a `requirement`.

## 3. Title and body

The **title** is what a search hits and what a list shows. Make it a short
phrase that names the subject, with the searchable words first:

- A noun phrase for most kinds: `Login p95 latency limit of 200 ms`.
- Past tense for a decision: `Chose bcrypt over argon2 for password hashing`.
- Under about 80 characters, no trailing period, no "we".

The **body** is a self-contained statement, readable by someone who never saw
the conversation that produced it. For a decision, say what was decided, why,
what was rejected, and what it affects. For the other kinds, say what a reader
needs to act on it.

- Keep the specifics: names, numbers, versions, paths, error messages. Do not
  generalise "the retry limit" into "some limits".
- No meta-language. "We discussed", "as mentioned above" and "the user said"
  point at a conversation the reader does not have.
- A few sentences to a short paragraph. If it needs headings or a list of more
  than a handful of items, it is a document: put it in the repository and link
  it by path from a short body.
- Never put a credential in either. The CLI refuses a title or body that
  matches a secret pattern.

## 4. When to write

Write an entry when:

- **A choice between alternatives is made.** Write it when you make it, not at
  the end. Include what you rejected.
- **The human confirms or states a requirement.** Record it in their terms.
- **Something was tried and rejected.** Record what and why, so nobody tries it
  again.
- **The session ends, or you stop with work unfinished.** Write one `handoff`.
- **A question is left open.** Write a `question`.

Do not write:

- Progress narration: what you read, ran or edited.
- What the code says. The code is the source for that.
- Anything derivable from the diff or the commit message.
- A second entry for something already recorded. Search first, and see
  [The reconcile loop](#7-the-reconcile-loop).

## 5. Tags

Run `inkentry memory tags` before you write and reuse a tag that fits before you
invent one. Keep them lowercase, hyphenated, and few: one to four.

```bash
inkentry memory tags
```

Tags are normalised on write ([ADR-101](https://github.com/inkentries/inkentry/blob/main/docs/adr/101-normalised-tags-and-linked-files-in-the-memory-projection.md)):
Unicode NFC, lowercased, with runs of whitespace or `_` turned into `-`, so
`Auth Service` and `auth_service` are the same tag. They are not stemmed or
aliased: `auth` and `authentication` stay two tags, which is why you check the
vocabulary first. A tag names a topic. Do not tag the kind (`decision`) or a
path (use `--files`).

## 6. Files

Pass `--files` with the repository-relative paths the entry is about, comma
separated:

```bash
--files src/auth/hash.rs,src/auth/session.rs
```

Link the files the entry constrains or explains, not every file you read.
Paths use forward slashes and are checked against git: `tracked`, `untracked`,
or `missing`. A `missing` path is still stored, with a warning, since a
decision about a file often comes before the file.

The link is what makes the entry surface at the moment it matters:
`inkentry memory list --file src/auth/hash.rs`,
`inkentry context --file src/auth/hash.rs` and
`inkentry search "<query>" --file src/auth/hash.rs` return the entries linked
to that exact path. An entry about the whole repository links no files.

## 7. The reconcile loop

Agent surfaces write with `--reconcile`. `memory add` then looks for active
entries that are near-restatements of the new one, and refuses to write until
you say how they relate. It embeds the entry to do this; if the embedder cannot
answer in time it compares titles only, and that never blocks a write.

```bash
inkentry memory add --reconcile --format json \
  --kind decision \
  --title "Chose bcrypt over argon2 for password hashing" \
  --body "Passwords are hashed with bcrypt at cost 12 in src/auth/hash.rs. Argon2 was rejected because the production image has no libargon2 and adding it would break the static musl build. Revisit if the image changes." \
  --tags security,auth \
  --files src/auth/hash.rs
```

**Exit 0** means the entry is written. The JSON names it and lists neighbours
that did not block:

```json
{
  "created": true,
  "entity_id": "d9719999a189708dbd9ce916d623abe5218c482274a4620b58cd010c977a426b",
  "id": "01a0ec5e-4848-77ef-a9b2-f717c363e59b",
  "kind": "decision",
  "title": "Chose bcrypt over argon2 for password hashing",
  "linked_files": [{"path": "src/auth/hash.rs", "state": "tracked"}],
  "related": [
    {"id": "01a0ec5e-4c30-7984-a9c0-6fb52eff6b51", "kind": "requirement",
     "title": "Login p95 latency limit of 200 ms", "created_at": 1790671998,
     "distance": 0.31, "band": "related"}
  ]
}
```

`linked_files`, `candidates` and `related` appear only when there is something
to show. `created` is `false` when an entry with identical kind, title and body
already exists; the command then reports it as already recorded.

**Exit 3** means nothing was written, because an existing entry is in the
duplicate band:

```json
{
  "created": false,
  "reason": "candidates",
  "candidates": [
    {"id": "01a0ec5e-4848-77ef-a9b2-f717c363e59b", "kind": "decision",
     "title": "Chose bcrypt for password hashing", "created_at": 1790671997,
     "distance": 0.09, "band": "duplicate"}
  ],
  "related": []
}
```

Read each candidate (`inkentry memory show <id>`), decide how your entry
relates to it, and repeat the same command with one resolution flag naming that
candidate's `id`:

| Flag | Meaning | Effect |
|---|---|---|
| `--supersedes <id>` | This entry replaces that one. | Archives the old entry and records a `supersedes` edge. |
| `--relates-to <id>` | Both stand, and they are related. | Records a `relates_to` edge. |
| `--contradicts <id>` | Both stand, and they disagree. | Records a `contradicts` edge. |
| `--distinct-from <id>` | Similar wording, different thing. | Records nothing. |

```bash
inkentry memory add --reconcile --format json \
  --kind decision --title "..." --body "..." --supersedes 01a0ec5e-4848-77ef-a9b2-f717c363e59b
```

Each flag takes one id, so with two candidates give two different flags, for
example `--supersedes <a> --distinct-from <b>`. The write goes through as soon
as one flag is present. The CLI does not check that you addressed every
candidate, so read all of them before you choose. An id that is not among the
candidates is accepted if it names a real entry.

Read `related` after every successful write. It lists entries that are close in
meaning but not restatements. A link can only be made when the entry is
written, so if a related entry is one your entry builds on, say so on the write
with `--relates-to`; to see what exists before you write, run
`inkentry memory list --file <path>`. If `related` shows you have just recorded
something that is already there in other words, `inkentry memory archive <id>`
removes the one you do not want from search.

## 8. Updates

An entry is immutable. To change what memory says, write a new entry that
supersedes the old one. Decide which case you are in:

| Situation | Write |
|---|---|
| **An update.** Same subject, a different conclusion, and the old one is no longer true. | A new entry with `--supersedes <old id>`. Its body stands alone; it is not a diff against the old one. |
| **A new entry.** A different subject. | A new entry, with `--relates-to <id>` if it builds on another. |
| **A contradiction.** Same subject, two conclusions, and someone still holds each. | A new entry with `--contradicts <id>`. Both stay active and `context` marks the conflict until a later decision supersedes one side. |
| **Already recorded.** Same subject, same conclusion. | Nothing. |

Do not leave a wrong entry active and add a note that says it is wrong. The old
entry stays retrievable with `--as-of` and `memory timeline`, so superseding it
loses nothing.

## 9. Caller declaration

Say who is calling. An agent that runs `inkentry` commands on purpose sets:

```bash
export INKENTRY_TRIGGER=explicit INKENTRY_ACTOR=agent INKENTRY_TOOL=claude-code
export INKENTRY_SESSION_REF=<session id> INKENTRY_MODEL=<model id>
```

`INKENTRY_TOOL` names the tool the agent runs in, and `INKENTRY_MODEL` the
model when it is known. A hook sets `INKENTRY_TRIGGER=hook` for the commands it
runs itself, so a read or write the agent chose is told apart from one that
happened automatically. An undeclared value reads as `unknown`; inkentry never
guesses it. The values feed the local event
log and an entry's `origin`; the session reference is stored only as a hash. See
the Caller declaration section of the
[config reference](https://github.com/inkentries/inkentry/blob/main/docs/config-reference.md).

## 10. Measured by

`inkentry metrics snapshot --json` reports whether agents follow this
([reference](https://github.com/inkentries/inkentry/blob/main/docs/commands.md#inkentry-metrics)):

- `rec.entries`, by kind and by origin: whether agents write, and what.
- `rec.supersede_rate`: whether updates are recorded as supersessions.
- `rec.near_duplicate_rate` and `rec.unresolved_conflicts`: whether the
  reconcile loop holds.
- `use.search_before_write`: whether writes follow a look at what exists.

## Out of scope

A structured decision schema, with options, criteria and outcome as fields,
needs its own ADR. Until then a decision is a title and a body written to the
rules above.
